# dan-mcnamara.com

Personal site: an intro page and a resume, built with Astro and hosted on GitHub Pages.
The resume is synced from the **Website** tab of a Google Doc.

```
Google Doc tab ──► sync-resume.yml ──► PR (src/data/resume.json) ──► merge ──► deploy.yml ──► GitHub Pages
                     Docs API → text → Gemini → Zod → PII scrub
```

## Layout

| Path | What it is |
|---|---|
| `src/data/resume.json` | Resume data (JSON Resume subset). Generated by the sync; safe to hand-edit. |
| `src/lib/resume-schema.ts` | Zod schema shared by the sync script and the site build |
| `src/lib/pii.ts` | Strips emails, phone numbers and address fields; the build fails if any remain |
| `src/pages/` | `index.astro` (intro) and `resume.astro` (resume + "Save as PDF") |
| `scripts/sync-resume.ts` | Doc → JSON pipeline (`npm run sync:resume`) |
| `.github/workflows/deploy.yml` | Push to `main` → test → build → deploy to Pages |
| `.github/workflows/sync-resume.yml` | Manual / Doc button / weekly → opens a PR when the resume changed |
| `apps-script/publish.gs` | Adds a "Website → Publish resume" menu to the Doc |
| `src/pages/concerts.astro` | "Shows": top 10 most-seen and 10 most recent artists |
| `src/data/concerts.json`, `src/assets/artists/` | Generated by `npm run sync:concerts` from setlist.fm + Deezer |
| `src/data/artist-overrides.json` | Pins a Deezer match by hand (see below) |
| `.github/workflows/sync-concerts.yml` | Manual / weekly → commits concert data to `main` and deploys |

## First run

```bash
npm install          # creates package-lock.json; commit it (CI uses npm ci)
npm test             # schema, PII and Doc-parsing checks
npm run dev          # http://localhost:4321
```

The seed `resume.json` was written by hand from the newest version in the doc.
The first sync replaces it with whatever is in the Website tab. Edit `basics.summary`
there or here; it's the paragraph on the home page.

## Setup checklist

### 1. GitHub Pages and the custom domain
The site is served at **https://dan-mcnamara.com** from the `DMcNamara/personal-site` repo.
With an Actions deploy, GitHub ignores any `CNAME` file; the domain is set in the repo settings.

1. **Settings → Pages → Source: GitHub Actions.**
2. (Recommended) Verify `dan-mcnamara.com` in your GitHub account: **Settings → Pages → Add a domain**,
   then add the TXT record it gives you. This stops anyone else from claiming the domain.
3. At your DNS provider, for `dan-mcnamara.com`:
   - `A` records: `185.199.108.153`, `185.199.109.153`, `185.199.110.153`, `185.199.111.153`
   - `AAAA` records: `2606:50c0:8000::153`, `2606:50c0:8001::153`, `2606:50c0:8002::153`, `2606:50c0:8003::153`
   - `CNAME` for `www` → `dmcnamara.github.io` (no repo name)
4. Repo **Settings → Pages → Custom domain:** enter `dan-mcnamara.com` and save.
5. Push to `main` (or **Actions → Deploy site → Run workflow**).
6. Once the DNS check passes, tick **Enforce HTTPS** (the option can take up to 24 hours to appear).

### 2. Google access (read-only)
1. In Google Cloud, create a project, enable the **Google Docs API**, and create a
   service account (no roles needed).
2. Share the resume doc with the service account's email as **Viewer**.
3. Pick one auth method:
   - **Quick start:** create a JSON key for the service account and save it as the
     repo secret `GCP_SA_KEY`.
   - **Keyless (recommended later):** set up Workload Identity Federation for this
     repo (see google-github-actions/auth docs), then set repo **variables**
     `GCP_WIF_PROVIDER` and `GCP_SERVICE_ACCOUNT`. The workflow uses this
     automatically when `GCP_WIF_PROVIDER` is set, and you can delete the key.

### 3. Gemini
1. Create an API key in Google AI Studio and save it as the repo secret `GEMINI_API_KEY`.
2. Optional: set the repo variable `GEMINI_MODEL` to pin a model. The default is the
   `gemini-flash-latest` alias. Each run sends one tab of text, so cost is a fraction of a cent.

### 4. Let Actions open PRs
**Settings → Actions → General → Workflow permissions:** check
"Allow GitHub Actions to create and approve pull requests."

### 5. Run it
**Actions → Sync resume from Google Doc → Run workflow** (also works from the
GitHub mobile app). Review the PR diff and merge; the deploy runs on merge.

### 6. Optional: publish button in the Doc
1. Create a fine-grained PAT limited to this repo with **Contents: Read and write**.
2. In the Doc: **Extensions → Apps Script**, paste `apps-script/publish.gs`, and add
   the token as the script property `GITHUB_TOKEN`.
3. Reload the Doc and use **Website → Publish resume**.

## Concerts page

```
setlist.fm "attended" ──► sync-concerts.ts ──► Deezer (photo, link, fans) ──► concerts.json + artists/*.jpg ──► commit ──► deploy
```

1. Request a setlist.fm API key (setlist.fm → Settings → API) and save it as the repo
   secret `SETLISTFM_API_KEY`. Locally, put it in `.env` (gitignored); the script reads it.
2. Optional: set the repo variable `SETLISTFM_USER` (default `dmcnamara1`).
3. **Actions → Sync concerts from setlist.fm → Run workflow**, or locally
   `npm run sync:concerts` (add `-- --dry-run` to print the JSON without writing).

Deezer has no key and is searched by name, so the sync only accepts an exact name match
and takes the one with the most fans. Once matched, an artist keeps the same Deezer ID on
later runs. To fix a wrong match, or hide a photo, add the setlist.fm artist's MusicBrainz ID
to `src/data/artist-overrides.json`:

```json
{ "78e854b8-9713-4ff2-9218-6b3784893bff": { "deezerId": 4037971 }, "<mbid>": { "deezerId": null } }
```

## Privacy

Email, phone and address never reach the site. The prompt tells the model to leave
them out, `scrubPII` removes them after the model runs, and the build fails if
anything matching an email or phone pattern is left in `resume.json`. The repo and
site are public, so treat `resume.json` as published.
